E-commerce Data Pipeline

An end-to-end batch pipeline built to learn dbt and Airflow on top of my SQL and BigQuery experience.
Extended in November 2026 with business logic testing, pipeline validation and CI/CD. See Phase 2.

The Motivation

After building a production SEO pipeline for Herd, I wanted more data engineering experience. I considered the Google Cloud Professional Data Engineer certification, but decided I needed hands-on projects more than another badge.

The SEO pipeline gave me solid SQL and BigQuery skills, but no experience of dbt or Airflow. So I built a pipeline from scratch rather than following a tutorial: my own dataset, my own design decisions, and the problems that only show up in real builds.

Phase 1: What I Built (May 2026)

A batch pipeline that loads e-commerce transactions into BigQuery one day at a time and transforms them into a tested star schema.

  • Incremental ingestion — A Python script loads one day's transactions per run, mirroring real-world batch jobs
  • Deduplication — Staging removes duplicate rows with ROW_NUMBER(), handling source duplicates and pipeline re-runs
  • Dimensional model — Staging cleans and flags quality issues; the marts layer builds a star schema with 2 dimensions and 2 fact tables
  • Automated testing — 22 dbt tests check primary keys and required fields
  • Orchestration — An Airflow DAG runs ingestion then dbt, with manual triggers and historical backfills

Technical Highlights

  • Airflow backfilling — Historical dates loaded one at a time with backfill commands
  • Quality flags over hard filters — Staging flags issues (negative quantities, missing customer IDs) instead of dropping rows, so analysts decide how to handle them
  • Composite quality flag — One is_valid_transaction field combines all quality checks for easy filtering
  • dbt model organisation — Three layers (staging, dimensions, facts), with tests alongside each layer's models
  • Raw layer as audit trail — Raw keeps everything received; deduplication happens in staging, so rules can change and be re-run
  • Full-refresh transformations — Simpler to build and validate; incremental models only pay off at larger volumes

Phase 2: Testing, Validation and CI/CD (Nov 2026)

I went back to make the pipeline check its own work. Writing tests and documentation uncovered two silent bugs, both now fixed.

  • Found and fixed a deduplication bug — The staging key assumed one line per product per invoice, so it removed genuine order lines (170 in the original 5-day load). A raw-to-staging reconciliation test now catches this; I reintroduced the bug to prove the test fails
  • Business logic tests — Six new tests (28 in total) check the numbers add up: staging reconciles to raw, line values and order totals match, one customer and one date per invoice, and totals have the right sign for the invoice type
  • Idempotent ingestion — Re-running a date replaces it instead of duplicating it
  • Validation in Airflow — The DAG now runs ingest → transform → test, and a failed test fails the run. Ingestion retries on brief failures; tests don't
  • CI/CD — Every push to GitHub rebuilds and tests all models in a separate BigQuery dataset, then publishes the dbt docs
  • Documented every model and column — Checking each model's code against what it was meant to do found a second bug: a window function's default frame blanked 17 product descriptions. Confirmed with a count, then fixed with an explicit frame
  • Loaded a full month — December 2010 (42,481 rows) gives the tests real edge cases to check

I also considered slowly changing dimensions and incremental models, and decided against both: the data doesn't change in ways SCD2 would capture, and at this volume a full rebuild takes seconds.
